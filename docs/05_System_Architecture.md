# System Architecture

## 1. Overview
SentinelAI is an end-to-end automated security operations platform. It
ingests raw security alerts, uses AI to classify and prioritize them,
manages the full incident lifecycle, and provides real-time visibility
through a reporting dashboard — all orchestrated via n8n workflows.

## 3. Component Breakdown

### 3.1 Alert Collection Layer
- **Purpose:** Ingest alerts from multiple heterogeneous sources
- **Implementation:** n8n workflow with webhook/API triggers
- **Output:** Normalized alert record → written to `alerts` table

### 3.2 AI Threat Classification Engine
- **Purpose:** Analyze alert content and assign severity + confidence score
- **Implementation:** n8n → LLM API call with structured prompt →
  JSON response (severity, category, false_positive flag)
- **Output:** Enriched alert data used to create an `incident` record

### 3.3 Incident Management Layer
- **Purpose:** Convert classified alerts into trackable incidents;
  auto-assign based on severity/team availability
- **Escalation Logic:** If a Critical/High incident remains "unassigned" or
  "unresolved" beyond SLA threshold → auto-escalate to IR team

### 3.4 Notification Layer
- **Purpose:** Notify relevant stakeholders at key lifecycle events
  (new incident, escalation, resolution)
- **Channels:** Email, Slack (extensible to SMS/Teams later)

### 3.5 Dashboard & Reporting Layer
- **Purpose:** Real-time visibility into incident status, trends, and
  team performance
- **Metrics Displayed:** Open vs resolved incidents, MTTR, severity
  distribution, SLA compliance rate

## 5. Data Flow Summary
1. Alert generated by a security source
2. n8n Workflow 1 collects & normalizes → stored in `alerts` table
3. n8n Workflow 2 sends alert to AI for classification → severity assigned
4. n8n Workflow 3 creates incident, assigns to team, applies escalation rules
5. n8n Workflow 4 tracks resolution status, updates database
6. n8n Workflow 5 aggregates data → powers dashboard/reports
7. Every step logged to `audit_logs` for traceability

## 6. Design Principles
- **Modularity:** Each workflow handles one responsibility (single
  responsibility principle applied to automation)
- **Auditability:** Every state change is logged
- **Fail-Safety:** Workflows include error handling/retry logic
- **Extensibility:** New alert sources or notification channels can be
  added without redesigning the core pipeline
